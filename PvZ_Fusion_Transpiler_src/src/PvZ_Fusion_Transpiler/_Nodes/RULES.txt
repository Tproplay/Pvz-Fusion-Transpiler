These rules must be followed for any changes inside the _Nodes folder.
(Rules 1-6 are the existing rules, with clarifications marked [clarified]. Rules 7-11 are new.)

1. Always return Plant and Zombie references in a wrapped class (Extentions/Entity/plant.py, Extentions/Entity/zombie.py).
   [clarified] This includes values returned from loops, triggers, TryX helpers and any container. Raw Plant/Zombie ports never leave an extension.

2. Always write __init__.py in every folder, and try to avoid direct imports from files like "from ..Original.Calculate.add_node import AddNode".
   [clarified] Extensions create nodes only through the factory functions in nodes.py, never by importing node classes from _Nodes/Original. Between extension modules, prefer importing from the package (the folder's __init__.py) over importing from a file.

3. Try not to make any function big. If that happens, divide it into classes and functions.
   [clarified] Guideline: about 40 lines or fewer per function, and no if/elif ladders that branch over types or variants (use a lookup table instead).

4. Taking inputs like PlantType, ZombieType must be handled through the enum; direct int input is not allowed.
   [clarified] This applies to every enum-backed input (PlantType, ZombieType, BulletType, ToolType, SoundType, KeyCode, SceneType, ...). Int sentinels such as -1 are not allowed either: use None or an explicit enum member. An enum value of the wrong type (for example a ZombieType given where a PlantType is expected) must raise TypeError. Existing APIs that still accept ints keep working but emit a DeprecationWarning.

5. Do not write the names of ports in Execution path like 创建成功, instead do self.node.port_output_plant_Plant.name
   [clarified] This applies to ExecutionPath(...), get_output(...) and any other port lookup: never use a port's display name as a string literal anywhere in extension code.

6. Extentions should only be focused on handling the Original nodes more easily, and should not be making a completely new functionality like arrays.
   These advanced functionalities will be present in extra libraries and not in the base library by default.
   [clarified] Allowed: thin wrappers (List[T] over the list nodes) and small compositions of Original nodes that a user would otherwise wire by hand (ForEach over a list, Clone, Time.WaitUntil).
   Not allowed: new data structures, algorithms or gameplay mechanics built on top of nodes (dictionaries, arrays, seeded RNG, key-driven movement).
   When unsure, put it in the extra library and note it in the report.

7. Use snake_case for functions and methods, and CamelCase for classes.

8. [new] No silent fallbacks. Unsupported types or arguments raise TypeError or ValueError with a message saying what to use instead. Never default to "int" or to the first match. Python operators that cannot work on graph values (len(), "in", bool(), iteration) must raise a helpful error rather than behave silently.

9. [new] Python-side state must not depend on which execution path ran. A method called inside a branch or loop must not rebind an extension object's ports or node references. The same Python object refers to the same node output on every path.

10. [new] Every new public API gets a snapshot test (the exact nodes and wiring emitted). Existing transpiled output must not change unless the change is documented in the agent report.

11. [new] Behaviour that has not been verified in the game is marked @experimental. Do not change existing lowering because of it.
